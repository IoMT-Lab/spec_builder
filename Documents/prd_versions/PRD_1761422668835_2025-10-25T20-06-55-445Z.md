# PRD for Photo Detector I²C Driver – Unit Tests

Executive Summary
- Project Overview
  - Objective: Establish a comprehensive, CI-friendly verification strategy for the PD_* I²C driver (AS7341 photo detector interface) implemented on an STM32WB0x-based platform. The driver supports register reads/writes and LED on/off control. The verification strategy combines host-based unit tests (Unity/CMock with a mocked I²C layer) and on-target integration tests (UART-based hardware harness) that exercise the full PD_* driver sequence on the embedded board with real sensor timing. Tests are integrated into CI (GitHub Actions) to flash firmware via OpenOCD/pyOCD, capture UART logs, and produce JUnit XML results.
  - Target Hardware and Driver: STM32WB0x (STM32WB05/STM32WB09) board running the PD_* driver for the AS7341 photo detector sensor.
  - Testing Approach:
    - Unit Tests: host-based, deterministic, using Unity/CMock with a mocked I²C backend to validate core driver logic (register semantics, LED state management, data path ingress/egress).
    - On-Target Tests: end-to-end integration on the STM32WB0x board using a UART-based hardware harness to exercise readiness waits, ID checks, threshold configuration, interrupt polling, and measurement validity with real sensor timing.
  - Success Criteria: ≥90% unit-test coverage for the driver module; reliable on-target integration sequences; deterministic CI results; well-documented test vectors and harness usage.
  - Deliverables: Reusable test harness, versioned test data sets, CI workflow (GitHub Actions) with OpenOCD/pyOCD flashing, UART log capture, and JUnit XML reporting.
  - Assumptions and Constraints:
    - Hardware access to the STM32WB0x board and AS7341 sensor is available for on-target tests.
    - The I²C timing model in unit tests can be made deterministic via mocks.
    - The PD_* APIs remain stable across iterations, or changes are reflected in tests with minimal friction.
  - Stakeholders: Software/Embedded Engineers, Quality Assurance, DevOps/CI engineers, Hardware/Systems team.

Objectives
- Deliver a maintainable, deterministic test suite that validates:
  - I²C operations and register semantics
  - LED on/off control behavior and interaction with other registers
  - Sensor data path conversions and data-ready signaling
  - End-to-end PD_* driver sequencing on hardware (readiness, ID, thresholds, interrupts, measurements)
- Achieve target coverage (≥90% for unit tests) and reliable CI runs with reproducible vectors
- Provide a clear, documented test harness, data sets, and guidance for extending tests as the driver evolves
- Ensure reproducible build/test environments and accessible test artifacts in CI

Product Overview
- Features
  - Unit tests for: I²C register reads/writes, LED on/off control, sensor data path, data-ready signaling, and error handling (timeouts, NACKs, bus errors)
  - Mocked I²C layer for host-based tests to simulate bus conditions without hardware
  - On-target integration tests via UART-based hardware harness to exercise the full PD_* driver sequence on STM32WB0x with real sensor timing (readiness waits, ID checks, threshold configuration, interrupt polling, measurement validity)
  - Reproducible test vectors and data sets, with documentation on test design and conventions
  - CI integration (GitHub Actions) with firmware flashing (OpenOCD/pyOCD), UART log capture, and JUnit XML test reports
- User Personas
  - Software Engineer (Primary): Builds and maintains the driver and tests; relies on deterministic unit tests and clear test data
  - Quality Assurance Engineer: Validates coverage, reliability, and CI reports
  - DevOps/CI Engineer: Automates test execution, reporting, and firmware flashing in CI
  - Embedded Maintenance Engineer: Extends tests as the driver evolves; references the test harness and data sets

Requirements
- I²C Read/Write Correctness
  - Acceptance Criteria:
    - Read/write operations return correct data for representative registers (configuration, status, data registers)
    - I²C transaction sequencing (start, address, data, stop) is correct; ACK/NACK handling is respected
  - Test Conditions:
    - Mock I²C layer returns predefined data; verify driver interprets data correctly
    - Simulate ACK/NACK on reads/writes; exercise error paths and recovery
- LED Control
  - Acceptance Criteria:
    - LED on/off commands mutate the driver state and do not interfere with other register operations
    - Repeated LED commands are idempotent (no unintended toggling)
  - Test Conditions:
    - Issue LED on/off sequences and verify internal state via mocks and any side effects
- Sensor Data Path
  - Acceptance Criteria:
    - Raw sensor data reads convert to expected engineering units or data formats; data-ready signaling behaves as specified
  - Test Conditions:
    - Provide representative raw values; verify conversions per datasheet and boundary conditions
- Error Handling
  - Acceptance Criteria:
    - Timeouts, NACKs, and bus errors surface as controlled error codes/statuses
    - Driver remains stable and can recover after transient bus errors where applicable
  - Test Conditions:
    - Simulate timeouts, NACKs, and bus errors; verify error paths and post-error recovery
- Reset/Power-up
  - Acceptance Criteria:
    - After reset/power-up, registers reset to defaults, LED is off, and data path is stable
  - Test Conditions:
    - Trigger reset and verify post-reset state matches expectations
- On-target Integration Tests
  - Acceptance Criteria:
    - End-to-end PD_* driver sequence validated on hardware: readiness waits pass, ID checks succeed, thresholds configure, interrupts occur, and measurements are valid
  - Test Conditions:
    - Run on STM32WB0x board with real sensor timing; verify sequence correctness and measurement outputs
- CI & Test Reporting
  - Acceptance Criteria:
    - CI runs produce deterministic results with clear pass/fail signals; JUnit XML reports and test artifacts are generated
  - Test Conditions:
    - Configure GitHub Actions to flash firmware, capture logs, and publish results
- Test Environment & Data Management
  - Acceptance Criteria:
    - Host unit tests with Unity/CMock and on-target tests with UART harness share deterministic data sets; test data is versioned and documented
  - Test Conditions:
    - Provide repository structure for test data, mocks, and harness configurations
- Performance and CI Readiness
  - Acceptance Criteria:
    - Tests run within defined time windows; minimal flakiness; suitable for CI with stable results
  - Test Conditions:
    - Run across representative environments; monitor for flakiness across repeated executions

Risk Assessment
- Technical Risks
  - Hardware timing differences could affect test determinism, especially on-target tests
    - Mitigation: Use deterministic mock timing for unit tests; define and enforce timeouts for on-target flows; decouple timing-sensitive code from logic where possible
  - Evolving register map or device features may render tests obsolete
    - Mitigation: Centralize register definitions; align tests with a single source of truth; update tests alongside driver changes
  - Flaky tests due to hardware initialization or UART logging issues
    - Mitigation: Stabilize harness boot sequence; add retry/logging guards; separate non-deterministic steps from core assertions
- Market/Adoption Risks
  - If hardware access is limited or varying hardware delays are encountered, end-to-end tests may be hard to maintain
    - Mitigation: Provide robust on-target test stubs or simulations; maintain a clear boundary between unit and integration tests; document hardware prerequisites
- Mitigation Strategies
  - Prioritize mocks and pure unit tests to minimize hardware variability
  - Maintain thorough test documentation and traceability to device datasheet registers
  - Automate test data generation and validation to prevent drift
  - Ensure CI includes reproducible environments and pinned tool versions

Notes
- This PRD focuses on unit testing for a photo detector I²C driver with LED control and on-target integration validation. If additional driver features (e.g., interrupts, advanced power modes) are introduced, extend the test suite with corresponding requirements and tests in a future update.
